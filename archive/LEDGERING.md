# Xeno Ledgering Plan

Status: implemented for all non-human-actionable items; remaining unchecked notes require product or upstream NetLedger decisions.

Owner decisions already made:

- One NetLedger tenant is created for each Xeno tenant.
- Xeno tenant creation, management, and deletion cascades to subordinate services, including NetLedger.
- One NetLedger account is created for each Xeno user.
- The requesting party is the authenticated Xeno API credential and its owning user.
- The serving party is the selected Xeno client and the user that owns that client.
- Ledger amounts are raw total tokens. No pricing, weighting, or provider-specific conversion is part of this release.
- Ledger writes must not sit on the synchronous completion or embedding serving path.
- NetLedger outages must not prevent Xeno from serving a request.
- Negative balances are allowed for now.
- Retry is in-memory only for this phase.
- System admins can see global ledger data, tenant admins can see tenant ledger data, and regular users can see only their own ledger data.
- Xeno's existing web dashboard is the product surface for ledger charts and tables. The standalone NetLedger UI is included in Docker for direct ledger administration, but it is not the Xeno user experience.
- Docker uses the existing Postgres container and initializes the NetLedger database alongside the Xeno database.
- Factory reset removes NetLedger data.
- NetLedger may still be improved where the improvement is generally useful outside Xeno.
- NetLedger v3.0.0 is the intended integration target. The local v3.0.0 source now includes tenant-aware ledger data and searchable label/tag metadata for accounts and entries.

## Why This Needs More Than A Thin API Client

Xeno already records the pieces needed to account for tokens. `RequestHistoryEntry` has tenant, requestor, credential, selected client, completion time, and `Telemetry.TotalTokens`. `XenoClientRecord` already has `OwnerUserId` and `OwnerCredentialId`, while `Credential` maps API keys to a `UserId`.

The missing part is durable ledger semantics around an asynchronous side effect. A request can complete successfully while NetLedger is down. A queued ledger event can be retried. A retry must not double-debit the requester or double-credit the serving client. Admin and user screens also need to enumerate records and trace them to Xeno requestor and serving-client identities. NetLedger v3.0.0 now gives Xeno the two large primitives the earlier draft asked NetLedger to add: tenant scope and searchable account/entry metadata.

The plan below treats correlation and idempotency as first-class work. Correlation should use NetLedger v3.0.0 labels and tags rather than custom entry columns. Idempotent creation is still not native in the v3.0.0 source reviewed here: entry IDs are generated by NetLedger, and credit/debit create requests do not accept an external idempotency key. Xeno therefore needs duplicate detection around tagged entries unless NetLedger adds a general-purpose idempotent create contract before the Xeno implementation lands.

## Product Scope

Ledgering applies to successful completion and embedding requests that produce a known `total_tokens` value. Each accounted request creates two ledger entries:

- A debit against the requesting user's NetLedger account.
- A credit against the serving client's owner user's NetLedger account.

The balance is a raw token balance. A requester with `-12000` has consumed 12,000 more tokens than they have earned or been granted. A serving user's account increases by the number of tokens their Xeno client served. No enforcement happens in this release, so the routing path never rejects a request because of balance.

The dashboard must present balances in a way that matches the viewer's scope:

- System admin: all tenants, global totals, per-tenant summaries, top debited users, top credited serving users and clients, queue health, and recent ledger activity.
- Tenant admin: one tenant, tenant totals, per-user balances, serving-client credit activity, queue health for that tenant, and recent ledger activity.
- Regular user: own balance, own debits, own credits from clients they operate, and recent ledger activity for their account.

## Non-Goals For This Release

Enforcement is deliberately out of scope. No preflight balance checks, reservations, quotas, spending caps, or route suppression should be added yet. Pricing is also out of scope: no dollars, multipliers, model-specific rates, or provider-specific token normalization.

Backfilling historical request history is not required for the initial release. The ledger starts accounting only after the feature is enabled, unless a later migration story is explicitly approved.

Persistent retry is also out of scope because the accepted retry model is in-memory only. Process crashes can lose events that were queued but not drained. Within a running process, event timestamps and identity references must be preserved exactly.

## Xeno Accounting Model

Xeno should create or resolve NetLedger objects lazily. Tenant and account creation should happen outside the request-serving path whenever possible, but a first-use lookup can still happen in the background drain worker.

Recommended Xeno records:

- `LedgerTenantLink`
  - `Id`, PrettyId prefix `ledten_`
  - `XenoTenantId`
  - `NetLedgerTenantId`
  - `CreatedUtc`, `UpdatedUtc`
- `LedgerAccountLink`
  - `Id`, PrettyId prefix `ledacct_`
  - `XenoTenantId`
  - `XenoUserId`
  - `NetLedgerTenantId`
  - `NetLedgerAccountId`
  - `CreatedUtc`, `UpdatedUtc`
- `LedgerQueueStatus`
  - in-memory status object, not persisted, reporting queue depth, oldest event age, last successful drain, last failure, and retry count

The account name should be deterministic and human-readable, but not relied on as the only identity. Use a stable name such as `xeno:user:{userId}` inside the NetLedger tenant and store the returned NetLedger account ID in Xeno platform state. For lookup and reconciliation, prefer the stored account ID first and tenant-scoped metadata enumeration second; do not depend on account-name lookup being tenant-scoped.

NetLedger account metadata:

- Labels: `xeno`, `xeno-user`.
- Tags:
  - `source`: `xeno`
  - `xenoTenantId`: the Xeno tenant ID
  - `xenoUserId`: the Xeno user ID
  - `xenoUserName`: optional display-safe user name or email if available

Debit and credit ownership rules:

- Request debit account: `RequestContext.CredentialId -> Credential.UserId`. If the request is authenticated as a user session instead of a credential, use `RequestContext.UserId`.
- Serving credit account: `RequestHistoryEntry.SelectedClientId -> XenoClientRecord.OwnerUserId`.
- Missing owner data: enqueue a ledger event with a terminal validation failure in queue status, log it, and do not block the request. Treat this as an operational bug to fix through client registration or data repair.
- Same user on both sides: write both entries. A user serving their own request should see both the debit and the credit, producing no net balance change but preserving activity.

Ledger event identity:

- One Xeno request produces one logical `LedgerEventId`, PrettyId prefix `ledevt_`.
- Debit entry identity: `ledgerEventId={LedgerEventId}`, `direction=debit`.
- Credit entry identity: `ledgerEventId={LedgerEventId}`, `direction=credit`.
- The `RequestHistoryEntry.Id` is stored as `requestHistoryId`.
- The request completion timestamp, falling back to request start time if completion time is absent, is stored in Xeno's `LedgerEvent` and in a sortable ISO-8601 `occurredUtc` entry tag. NetLedger `CreatedUtc` remains the time NetLedger accepted the entry.

NetLedger entry metadata:

- Labels: `xeno`, `xeno-token-usage`, and either `xeno-debit` or `xeno-credit`.
- Tags:
  - `source`: `xeno`
  - `ledgerEventId`: the logical Xeno ledger event ID
  - `direction`: `debit` or `credit`
  - `xenoTenantId`: the Xeno tenant ID
  - `requestHistoryId`: the Xeno request history ID
  - `requestCredentialId`: the credential that requested the work, when present
  - `requestUserId`: the user charged for the request
  - `selectedClientId`: the Xeno client that served the request
  - `servingUserId`: the owner of the serving client
  - `counterpartyUserId`: the other user in the debit/credit pair
  - `requestKind`: `completion` or `embedding`
  - `occurredUtc`: the business event timestamp in round-trip UTC format

Tag values should be short, stable identifiers. Human-readable details belong in Xeno APIs or descriptions, not in tags used for machine filtering.

## Server Architecture

Ledger writes should be captured after request history has been populated and saved. At that point Xeno knows whether routing succeeded, which client served the request, which user/credential requested it, and how many total tokens were reported.

Add the following server components:

- [x] `LedgerSettings` in core settings:
  - `Enabled`
  - `BaseUrl`
  - `ApiKey`
  - `SecretKey`
  - `DrainIntervalMs`
  - `MaxBatchSize`
  - `MaxQueueDepth`
  - `RequestTimeoutMs`
  - `CreateTenantsAutomatically`
  - `CreateAccountsAutomatically`
  - `CommitEntriesImmediately`
- [x] `LedgerEvent` model with all IDs, total tokens, request path kind, timestamps, and retry metadata.
- [x] `LedgerEntryDirection` enum with `Debit` and `Credit`.
- [x] `LedgerAccountResolver` to map Xeno tenant/user records to NetLedger tenant/account records.
- [x] `NetLedgerClient` wrapper using Xeno's HTTP and JSON conventions, with cancellable async methods and `ConfigureAwait(false)`.
- [x] `LedgerQueue` based on `System.Threading.Channels` or a comparable in-process queue.
- [x] `LedgerDrainService` background worker that drains batches on interval, retries failed entries in memory, and emits health counters.
- [x] `LedgerService` facade used by request handling and APIs.

The request-serving code should do the smallest possible amount of work:

1. Confirm ledgering is enabled.
2. Confirm the request succeeded and has `Telemetry.TotalTokens > 0`.
3. Confirm requestor and selected client IDs are present.
4. Build a `LedgerEvent` from already-loaded request history and client data.
5. Try to enqueue it.
6. Log and increment a counter if enqueue fails because the queue is full or the event is invalid.

No call to NetLedger belongs in that path. Account creation, NetLedger tenant creation, debit writes, credit writes, and commit calls belong in the drain worker.

## Drain Behavior

The drain worker must preserve event fidelity during the process lifetime. It cannot collapse entries into aggregate totals before writing them, because admins and users need request-level ledger records and because duplicate-safe retry depends on stable metadata tags.

Drain algorithm:

- [x] Pull up to `MaxBatchSize` events.
- [x] Resolve or create the NetLedger tenant link for each Xeno tenant.
- [x] Resolve or create the debit account for the requesting user.
- [x] Resolve or create the credit account for the serving client's owner user.
- [x] For each debit/credit target account, search existing entries by labels/tags for `source=xeno`, `ledgerEventId`, and `direction`.
- [x] Treat an existing matching entry as success and record its NetLedger entry ID in drain diagnostics.
- [x] Write one debit entry and one credit entry with the stable labels and tags listed above when no matching entry exists.
- [x] Commit entries immediately if NetLedger requires commit for balances to reflect them.
- [x] Retry transient failures in memory with bounded exponential backoff and jitter.
- [x] Stop retrying terminal validation failures, keep them in queue status until restart or explicit clear, and log enough context to repair the data.

Commit strategy should use NetLedger's already-committed credit/debit create support if the compatibility smoke test confirms balances update as expected. If any SDK or REST path does not honor immediate commit, create pending entries and call commit as part of the same drain attempt.

## Rollout Plan

Start behind configuration. Ledgering should be disabled by default for existing non-Docker installs until the operator supplies NetLedger settings. The Docker developer environment can enable it because the compose file supplies NetLedger.

Suggested rollout sequence:

1. NetLedger v3.0.0 compatibility verification for tenant APIs, metadata filters, immediate commit, and Docker images.
2. Xeno settings, metadata schema, models, account links, queue, drain worker, and fake NetLedger tests.
3. Tenant lifecycle cascade coordinator and NetLedger subordinate service.
4. Request path enqueue integration for completions and embeddings.
5. Xeno ledger APIs and OpenAPI.
6. Dashboard ledger page.
7. SDKs, CLI, Postman, and docs.
8. Docker compose, Postgres initialization, and factory reset integration.
9. End-to-end verification and release notes.

Do not enable enforcement in a follow-up by bolting checks into routing ad hoc. Enforcement needs its own design around reservations, pending usage, fail-open versus fail-closed policy, admin overrides, and what to do when token usage is only known after streaming completes.
